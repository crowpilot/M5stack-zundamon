# 再学習を含む反応速度改善案（2026-10-18）

**設計検討用の資料。今回は訓練を実施せず、現行モデル・語彙・音声バンクも変更していない。** 効果は未検証で、短縮時間や品質向上を数値では約束しない。現在進めているキャッシュ、処理の重複削減、先行計算とは分けて判断する。

最初に試す候補は、既存の出力形式を保った「短い第一句を生成するLLMの調整」。音声認識の終了後処理が引き続き支配的なら、次にストリーミングASRを検討する。音声向けの出力形式・語彙の変更は、LLMと読み上げ側を一緒に評価できる段階で扱う。

## 現行構成を実装から確認した結果

| 部分 | 確認できた構成 | 最適化を考える上での制約 |
| --- | --- | --- |
| ASR前処理 | 16kHz、40メル特徴。窓400サンプル、hop160、FFT512。発話全体の平均・分散によるCMVN | 発話が伸びると既存フレームの正規化値も変わる。FFT等を先行計算しても、そのまま確定済みの認識結果にはならない |
| ASRネットワーク | Conv1d＋ReLUを2段（各64ch、kernel5、stride2、左右padding）、双方向GRUを2層（各方向hidden64）、86クラスの線形出力とCTC復号 | 畳み込みの右側入力、逆方向GRUが未来の音を使う。現行重みで一方向だけを動かしても同じ認識にはならない |
| ASR重み | `kana_asr.bin`は718,800B。実装は重みをfloat32配列として参照し、floatで積和 | 依頼元資料の「int8」と実ファイル／推論実装は一致しない。量子化の検討では現行float32を比較基準にする |
| LLM | Q8、group size32。dim96、hidden256、6層、6 attention heads、KV3 heads、語彙1,024、最大系列256。重み799,912B | 現状でも小さいモデル。層数・幅・語彙を変更すると品質だけでなく端末上の演算効率も変わる |

| 読み上げ | 漢字かな交じりの返答→辞書／規則で読み・アクセント記法→モーラ列→既存VCV音声単位を接続 | 端末でニューラル音声生成モデルを走らせている構成ではない。TTSモデル再学習がそのまま次の速度改善になるとは限らない |

## 1. 発話中に進められるASRへ変更

**区分：ASR単体の再学習＋録音／確定処理との統合変更。**

- **目的**：話し終わってから全発話を処理する負担を減らす。全発話CMVNを学習集合の固定統計や過去方向だけの正規化へ置き換え、畳み込みも因果的または有限の先読みとし、一方向GRU等で状態を引き継ぐ。小さな先読み窓を残す案も比較する。CMVNだけ、または逆方向GRUだけを削る置換では成立しない。
- **必要データ**：音声と正解かな。実機マイクの距離、声量、生活音、話者差を含める。自然な言いよどみ、途中の間、長音、訂正、登録外の発話を入れ、音声を連続チャンクとして学習・評価する。現行ASRの出力を教師にした蒸留は補助候補で、正解文字による評価は残す。
- **品質測定**：かなの文字誤り率、登録フレーズの正答／誤受理／棄却、登録外入力の扱い。途中結果の書き換え頻度、確定を早めて失う語尾、発話中のCPU使用・録音取りこぼしも測る。学習と評価で話者・録音を分離する。
- **実行判断**：実機計測で発話終了後のASRが大きな待ち時間として残り、端末が録音と増分推論を両立できる場合に着手する。固定の発話終了待ちを維持する限り、その待ち自体は残る。途中認識をLLMへ渡す場合は、確定条件と訂正時の破棄を別途設計する。

## 2. 意味のある短い第一句を学習する

**区分：LLM単体の追加学習。現行の文字列＋末尾感情タグの形式を維持する案を先に試せる。**

- **目的**：TTSが最初の句読点まで待つ時間を減らす。まず短い第一句で入力に応じた内容を返し、必要な補足を次の句へ回す。単に生成上限を切り詰めたり、どんな入力にも同じ相づちを挿入したりする方法とは区別する。
- **必要データ**：入力、自然で短い第一句、必要な続き、感情タグを揃えた対話例。あいさつだけでなく、質問、気持ちの共有、否定、聞き取りが曖昧な入力も含める。既存の返答と短縮版を対にし、語尾やずんだもんらしさを保つ。
- **品質測定**：最初の句読点までのトークン数に加え、実機で「意味のある返答が聞こえ始めるまで」を測る。質問への適合、情報の脱落、不自然な句切り、同じ前置きの反復、全文の自然さ、温度0.8での多様性も比較する。
- **実行判断**：入力準備を速くした後も第一句の生成が待ち時間の中心なら優先する。内容や自然さを保ったまま改善する設定だけを採用する。返答形式を変えないため、他案より既存パイプラインとの比較を作りやすい。

## 3. 読み・声色を早く渡せるLLM出力形式と語彙

**区分：LLMの再学習＋生成／表示／読み上げを合わせた設計。ASRまで同時に再学習する必要はない。**

- **目的**：現在は最後に付く感情タグと、第一句時点の感情推定のずれを減らし、読み上げに必要な情報を先に確定する。例えば「声色→第一句の読み→句終了」の単位を学習し、表示文との対応を持たせる。別案として、本文を保ちながら小さな読み／声色予測ヘッドを追加する。読みをかな1文字ずつ生成すると逆にトークンが増える可能性があるため、モーラや頻出語句単位の語彙も比較する。
- **必要データ**：入力、表示文、文脈に合う読み、句境界、声色の対応。辞書が苦手な漢字、数字、固有名詞、疑問形を含める。自動生成した読みと声色は確認し、既存音声バンクで発音できる単位へ正規化する。
- **品質測定**：読みの正確さ、表示文と音声の一致、句境界の自然さ、声色の妥当性、途中で声色を変えたくなる割合。語彙サイズ・分類層の負荷・第一句までの実トークン数・RAM／Flashを合わせて測る。表示用文と読みを直列で二重生成する負担も含める。
- **実行判断**：単なる辞書引きの削減だけを目的にしない。現行の辞書処理は比較的軽く、読みに必要な追加トークンの方が高くつく可能性がある。第一句と声色が早く安定し、端末全体の時間も改善すると確認できる場合に採用する。

## 4. 蒸留・小型化・量子化への適応

**区分：まずASRまたはLLMを片方ずつ再学習。両方を同時に変更せず、原因を切り分ける。**

- **目的**：ASRの層数・幅を抑える、LLMの層数・幅・FFNを減らす、学習時に量子化誤差へ適応させる等で、端末での計算量と転送量を減らす。ASRはfloat32からの整数化、LLMは現在のQ8からさらに小さい表現を検討する余地がある。
- **必要データ**：現モデルの教師出力に加え、正解を持つ実音声・対話例。登録29文だけで蒸留すると登録外入力の能力を失いやすいため、想定範囲の入力分布と難例を含める。量子化の校正データは、学習用・最終評価用と役割を分ける。
- **品質測定**：ASRは認識・誤受理、LLMは応答の意味・語尾・読み上げ可能性・温度0.8での崩れを測る。量子化後のCore2実装で時間・メモリを測り、ファイルが小さいことを速度向上の代用にしない。
- **実行判断**：先に端末で使える積和カーネルと展開コストを確認する。低ビット化で毎回の展開が増えたり、非構造的な枝刈りが通常の密行列計算のままになったりすると速くならない。学習済みモデルの層をそのまま削る方法は避け、候補を蒸留／再学習して比較する。

## 5. 音声認識と対話を共通の表現でつなぐ

**区分：統合を前提とした再学習。単体の高速化より変更範囲が広い。**

- **目的**：ASRのかな→登録フレーズ照合→LLMの文字トークン化という受け渡しを見直す。段階案は、ASRにフレーズID／意図の補助出力を持たせる、LLM入力に同じID表現を学習させる、認識の曖昧さを複数候補として学習する、というもの。音声特徴から返答までを直接生成する全面的な統合学習は、その先の別案として扱う。
- **必要データ**：同じ実音声に、正解文字、登録フレーズまたは登録外のラベル、意図、適切な返答を対応付ける。似た発音、雑音、途中まで同じ文、対象外の発話を十分含める。音声→返答だけのデータでは、認識失敗と対話失敗を切り分けにくい。
- **品質測定**：登録外入力を既知フレーズへ押し込む割合、誤った意図に即答する割合、曖昧な入力への応答、話者が変わった場合の性能。最終返答だけでなく、認識文字／意図の中間結果も評価できる形を残す。
- **実行判断**：現在の登録フレーズID→事前トークン／KVキャッシュで目的を達成できるなら、その方法を先に使う。直接ID表現の再学習は、対応範囲を広げる必要があり、自由入力への戻り先も維持できる場合に検討する。全面的な音声対話モデル化を、再学習なしの部品連携と混同しない。

## 比較と着手の順序

1. 現行モデル＋今回の実装最適化を基準に、発話終了待ち、ASR、入力準備、第一句生成、TTS、実際の発声開始を分けて測る。平均だけでなく遅いケースと誤応答も残す。
2. 支配的な待ち時間に対応する案を一つ選ぶ。第一句生成が残るなら案2、ASRが残るなら案1、読みや声色も改善対象なら案3を候補にする。案4は端末カーネルの見込みを確認してから、案5は必要な対応範囲が既存連携を超えてから判断する。
3. 学習に使わない評価セットを先に固定する。同一録音・同一対話の言い換えが学習側へ混ざらないようにし、通常入力と難例の両方を同じ条件で比較する。
4. 別モデル名・別語彙・別キャッシュidentityで候補を作り、ホストの品質確認後にCore2で測る。既存モデルと音声バンクは戻せる状態で保持する。モデル／語彙変更後のpromptキャッシュを流用しない。

**現段階で決めるのは次の実験対象まで。訓練開始、学習資源の使用、現行モデルの差し替えは、この資料では実施・完了扱いにしない。**

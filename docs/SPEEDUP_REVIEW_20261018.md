# M5Stackずんだもんの音声応答を早める調査

2026年10月18日。対象は v0.0.3、commit `f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317`。依頼書は [SPEEDUP_REQUEST.md](SPEEDUP_REQUEST.md)。SDカード、ネットワーク、サーバーを使わず、Core2と現在のVCV音声合成方式を維持する前提で評価した。

**最初に試すのは、固定プロンプトの再利用、プロンプト途中の不要な出力計算の省略、文字を読み上げへ渡すタイミングの修正、音声先頭の無音短縮である。** 発話終了判定も調整できれば、現状から合計0.7〜1.0秒程度を削る試算になる。これは実機で達成した値ではなく、125ms/forwardという依頼書の測定値に基づく検証目標である。

フラッシュ律速は有力な仮説だが、**「現在40MHzで動作している」という前提から確認し直す必要がある**。ローカルのビルド済みバイナリは、PSRAM初期化時にフラッシュとPSRAMを80MHzへ設定する構成だった。ボード定義や起動ヘッダーの40MHzだけを見て、80MHz化による2倍の改善を見込むことはできない。

調査として、ソース、モデル、ビルド済みESP32バイナリの逆アセンブル、PC上の計算一致、Espressif等の一次資料を確認した。ファームウェア本体と実機の設定は変更していない。実機での短縮量、音切れ、認識精度、QIO安定性は、以下の実装と測定に残る。

## 現在の待ち時間と計測の注意点

待ち時間は次のように分かれる。

```text
人の発話終了
  → 無音判定 700ms
  → 音声認識 300〜600ms
  → プロンプトのforward N回
  → 最初の句が成立するまでの生成
  → 読み変換とTTS 35〜90ms
  → スピーカーへ登録
  → 再生側の待ちとPCM先頭の無音
  → 実際に声が聞こえる
```

プロンプトは6〜16トークンの例で約0.75〜2.0秒を占める。したがってプロンプト処理を優先する判断は正しい。一方、700msの発話終了待ちは計算最適化とは独立して削れる。

現行の時間項目には、次の違いがある。

| 項目 | 実装が測っている時点 | 解釈 |
| --- | --- | --- |
| `first_piece_ms` | 最初の文字片のコールバック到達 | 最初のトークンが決まった直後ではなく、そのトークンをもう1回forwardした後 |
| `first_sound_ms` | `M5.Speaker.playRaw()`呼び出し直後 | 音声を登録した時点。実際の音響的な発声開始ではない |
| `llm_ms` | `zunda_brain_reply()`の全期間 | コールバック内の画面描画、読み変換、TTS、キュー待ちも含む |

根拠は [zunda_brain.cの生成ループ](https://github.com/crowpilot/M5stack-zundamon/blob/f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317/firmware/src/zunda_brain.c#L73)、[main.cppの音声登録](https://github.com/crowpilot/M5stack-zundamon/blob/f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317/firmware/src/main.cpp#L293)。時間項目の定義を変える場合は、従来値と同じ名前で比較しない。

## 短縮候補の比較

潜在効果の大きいものから並べた。幅が重なるため厳密な順位ではない。数値は特記しない限りN=6〜16、125ms/forwardを使う条件付き試算であり、各行を単純加算できない。実装の手間は、小が局所変更、中が複数処理の変更、大が推論経路や学習の変更を意味する。

| 候補 | 見込める短縮幅と条件 | 手間 | 品質とメモリへの影響 |
| --- | --- | --- | --- |
| 登録フレーズの返事を事前計算 | ヒット時、提示例では約1.3〜2.2秒。LLM待ちの大半を除去 | 中 | 現行greedyの返事・タグを保存すれば同じ内容。モデル更新で再生成。文章だけなら数KB〜数十KB |
| プロンプトを層ごとに一括処理 | 約0.2〜1.5秒。ただし読み出し待ち割合30〜80%という仮定。CPU律速なら小さい | 大 | 数値の計算順に注意。追加作業領域は実装次第で数十KB以上 |
| DIOからQIOへ変更 | 実行時DIO/80MHzなら約0.1〜0.7秒の試算。効果ゼロもあり得る | 小〜中 | モデル品質は同じ。対象フラッシュ、ブートローダ、実機の安定性確認が必要 |
| 6層から4層のモデルへ変更 | 線形層の仕事量に比例すると、プロンプト部分で約0.22〜0.57秒 | 大 | 再学習・蒸留・品質評価が必要。重みとKVは減る。単なる層の削除は不可 |
| 行列計算を2コアへ分担 | 理想的には並列化対象部分の最大半分を短縮。全forwardが半分になるわけではない | 中 | バス競合と同期でゼロ改善・悪化もある。ワーカー用内部RAMと音声タスクとの調整が必要 |
| 発話終了判定を700→350〜500msへ | 0.20〜0.35秒 | 小〜中 | 途中の言いよどみを終了と誤判定しやすい。ASR入力末尾の長さも変わる |
| 固定のBOSとＡ：を再利用 | 約0.25秒 | 小 | 同じモデル・語彙なら計算結果を維持。KVスナップショットは4,608B |
| プロンプト途中の分類層を省略 | 計算量比例の目安で約0.09〜0.26秒 | 小 | 最後のプロンプトの分類は残す。出力品質の変更不要 |
| LLM重みをPSRAMへコピー | ASRと同じ「速度1.14倍」が出た場合、プロンプトで約0.09〜0.25秒 | 中 | この速度比はLLMには未確認。799,912Bの領域が必要。今の空きだけでは不足 |
| 確定済み文字を次のforwardより先に通知 | 最初の句が句読点で切れる例では約0.125〜0.14秒 | 小〜中 | 本文・最終タグは維持できる。途中の声色推定は仕様調整が必要 |
| TTS先頭の無音を100→20〜30msへ | 通常レートで実際の発声開始を約0.07〜0.08秒短縮する候補 | 小 | 語頭の自然さ・ノイズを聴いて確認。`first_sound_ms`には改善が現れない |
| TTS本体の高速化・小分け合成 | 現在の初回合成35〜90msの一部分 | 中〜大 | VCV接続・抑揚・途切れへの影響がある。初手の効果は小さい |

量子化の重複除去、RoPEの再利用、小さな作業配列の内部RAM化も優先候補である。これらは現状の区間別時間がないため、秒数を断定しない。**1forwardが5ms短くなれば、提示例のプロンプトだけで30〜80ms短くなる**。先に各区間を計測し、毎回発生する時間を狙う。

## まず実装する小さな変更

### 固定2トークンのKVを再利用する

現在の語彙を実際にトークン化すると、`<BOS>Ａ：`はトークンID `[1, 3]`、2トークンだった。

```text
必要なKV = 2トークン × K/Vの2種類 × 6層 × 48要素 × 4B
         = 4,608B
```

起動時に2トークンだけforwardし、次の発話から位置2で開始する。先頭2位置を一切上書きしない実装なら、既存KV内にそのまま保持して追加コピー領域を省くこともできる。`Ｂ：`は話しかけの後にあり、位置と文脈に依存するため固定のKVとして再利用できない。

モデル・トークナイザを差し替えたら必ず再計算し、先頭のトークン列が同じことを確認する。ID `[1,3]`を新語彙へ無条件に引き継がない。

### プロンプトの最後以外では語彙への出力計算をしない

[llm_core.cの末尾](https://github.com/crowpilot/M5stack-zundamon/blob/f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317/firmware/src/llm_core.c#L293)は、全forwardで最終RMSNormと`1024×96`の分類を行う。しかしプロンプト読み込みループは、その途中のlogitsを使わず捨てている。

`llm_forward(..., need_logits)`のように分け、途中はKV作成後に戻る。最後の`Ｂ：`では従来どおり全語彙を計算する。

```text
Transformerの線形層   608,256 MAC / token
分類層                 98,304 MAC / token
合計                  706,560 MAC / token
分類層の割合               13.91%
```

13.91%は線形層の積和数の割合であり、実時間の実測比ではない。仮に1回17.4msなら、N−1回の省略で87〜261msになる。固定2トークン再利用も入れた後は、省く回数がN−3回になるので、両施策の効果を重ねて数えない。

PC上では、登録29フレーズと依頼書の追加3文について、固定KV再利用と途中分類省略を組み合わせた後のKV、最終logits、以後のgreedy生成logitsが元の計算とビット単位で一致した。これは現在のモデルで計算を省ける確認であり、ESP32上の速度測定ではない。記録は [ホスト確認結果](SPEEDUP_HOST_CHECK_20261018.txt)。

### 確定した文字をすぐに読み上げ側へ渡す

現行は次の順序になっている。

```c
next = argmax(logits);          // この時点で出す文字は決まっている
piece = llm_decode(...);
logits = llm_forward(next, ...); // 約125ms待つ
on_piece(piece, logits);        // ここで初めて表示と読み上げに渡す
```

そのためPC上の呼び出し回数でも、N=6なら最初の通知まで7forward、N=16なら17forwardだった。`on_piece`をforwardの前へ移す、または「文字確定」と「次位置のlogits確定」の通知を分けると、この待ちを避けられる。

ただし現在は、句読点を取り込んだ**後**のlogitsで声色を決めている。通知だけ移して引数を同じ意味と扱うと、声色の判定位置がずれる。最初は通常の声色、または一つ前のlogitsのタグ予測を使う、と明示する必要がある。本文と最後に付く気持ちタグは従来どおり生成できる。声色まで完全に従来どおりに保つ場合は、同じ125msを待つ必要がある。

句読点がなく、生成終了後の`talk_end()`で初めて句を送るケースでは、この変更だけで125ms短くなるとは限らない。

### TTS先頭の100msの無音を短くする

[tts.cppのrender開始時](https://github.com/crowpilot/M5stack-zundamon/blob/f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317/firmware/src/tts.cpp#L106)は`ensure(sr_ / 10)`で100ms分のゼロを作り、その後ろに最初の単位を置く。これは計算時間とは別に、再生開始後の無音になる。

初回の先頭余白を20〜30msにして音を確認する価値がある。各句へ付く余白も会話の間に影響するが、VCVの接続アンカーと末尾処理を一緒に壊さない。PCMの非無音開始位置と実際の録音で評価する。

## フラッシュ律速の仮説と設定の確認

### 125msと読み出し量の一致だけでは律速を確定できない

モデルファイルは799,912B。全語彙分類を行う現状では、1tokenに約0.8MBの重み・倍率を参照するという見立ては概ね正しい。DIO/40MHzのデータ線部分の理論上限は10MB/s、DIO/80MHzは20MB/s、QIO/80MHzは40MB/s。実際にはコマンド、アドレス、dummy cycle、キャッシュの入れ替え、命令実行が加わる。

Espressifの説明では、キャッシュ読み出しは1コマンド32Bで、QIO/DIOの差はキャッシュミス時の補充速度に現れる。処理全体の倍率にはならない。[SPI Flash Modes](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/spi-flash-modes.html)

`0.8MB ÷ 125ms ≈ 6.4MB/s`は処理時間から逆算した値であり、フラッシュ帯域を独立に測定した値ではない。これを使って125msを再現しても仮説の証明にはならない。

ローカルのESP32用ELFの`matmul`では、int8積和1要素がロード2回、符号拡張、乗算、加算、アドレス計算、ループ分岐などになっていた。1MACが1cycleという実装ではない。さらに入力量子化では各要素に`__divsf3`と`roundf`が呼ばれ、PSRAM対策の`memw`も入る。したがって「約70万MACなので推論全体は10〜30msで済む」は、まだ裏付けのない見積もりである。

### 実行中は既にフラッシュ80MHzの可能性が高い

次の証拠が併存している。

| 確認箇所 | 内容 |
| --- | --- |
| PlatformIO 6.9.0のCore2定義 | DIO、40MHz |
| ローカルの`bootloader.bin`と`firmware.bin`ヘッダー | DIO、40MHz |
| Arduino-ESP32 2.0.17の組み込みSDK設定 | `CONFIG_SPIRAM_SPEED_80M=1`、`CONFIG_ESPTOOLPY_FLASHFREQ_80M=1` |
| ビルド済みELFの`esp_spiram_init` | 第1引数2で初期化関数を呼ぶ。SDKのenumでは`PSRAM_CACHE_F80M_S80M` |
| ESP-IDFのPSRAM初期化実装 | このモードでフラッシュのキャッシュ側・アクセス側のクロックを80MHzへ設定する |

PSRAM初期化が元のフラッシュ速度を上書きすることは、[ESP-IDF v4.4.7の実装](https://github.com/espressif/esp-idf/blob/v4.4.7/components/esp_hw_support/port/esp32/spiram_psram.c)にも明記されている。[モードの選択処理](https://github.com/espressif/esp-idf/blob/v4.4.7/components/esp_hw_support/port/esp32/spiram.c)も同じ組み合わせを使う。

**このビルドが実機で動いているなら、推論時はDIO/80MHz、PSRAM/80MHzになっている可能性が高い。** 実機レジスタは未取得なので、40MHzとも80MHzとも実測値として断定しない。`setup()`後の`SPI_CLOCK_REG(0/1)`、`SPI_CTRL_REG(0)`、`SPI_DATE_REG(0)`等を、そのIDF版の定義に沿って読み、実効分周とQIO/DIOを確認する。`ESP.getFlashChipSpeed()`や起動ヘッダーだけで設定後の速度を保証しない。

### QIO化とブートローダ

80MHz自体には、[Arduino-ESP32 2.0.17のCore2定義](https://github.com/espressif/arduino-esp32/blob/2.0.17/boards.txt#L12659)と[M5Stack公式Core2サンプル](https://github.com/m5stack/M5Core2_Weather_Dashboard/blob/main/sdkconfig.defaults)がDIO/80MHzを使う先例がある。一方、提示のJEDEC IDだけでは、実装されているフラッシュの正確な品番・電気条件・QIO有効化手順まで確定できなかった。

QIOは有望な比較対象として扱う。設定案は次のとおり。

```ini
board_build.flash_mode = qio
board_build.f_flash = 80000000L
```

PlatformIOのArduino用ビルドスクリプトではflash modeに応じたSDKディレクトリを選ぶ構造になっている。実装時はverbose buildで`qio_qspi`の選択とブートローダを確認し、クリーンビルドして必要なブートローダも更新する。アプリだけのOTAでモードが切り替わると考えない。QIO構成でも初期ブートをDIOで行う場合があるため、ヘッダーだけで成否を判定せず、初期化後のモードを確かめる。[EspressifのFlash Mode説明](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/spi-flash-modes.html)

実行時の変更がDIO/80→QIO/80なら、帯域部分の改善上限は概ね2倍の側で考える。例えば全forwardの30〜70%が改善対象の待ち時間で、その部分が2倍になるなら、全forwardの短縮は15〜35%。125msなら約19〜44ms/回である。キャッシュ、計算、TTSが残るので全体4倍は見込まない。

フラッシュとPSRAMは並列接続され、同じキャッシュ領域を使う。32KBを超える大きなアクセスではキャッシュが足りず、外部メモリ速度とキャッシュ追い出しの影響が出る。80MHzの外部RAMがHSPI/VSPIの一方を必要とする制約もある。周波数設定を変える際は、LCD等が使うSPI hostとの整合も確認する。[ESP-IDF 4.4.8の外部RAM制約](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32/api-guides/external-ram.html#restrictions)

## 演算とメモリ配置で改善できる箇所

### 入力量子化を共有する

現在の`matmul()`は呼ぶたびに入力を量子化する。各層のQ/K/Vは同じ`xb`を使い、FFNのw1/w3も同じ入力を使うため、前者3回を1回、後者2回を1回にできる。元の[llama2.cのrunq.c](https://github.com/karpathy/llama2.c/blob/master/runq.c)も、この形で量子化結果を共有している。

現在は全forwardで入力要素5,088個分を量子化する。共有すれば3,360個になり、1,728要素分の除算・丸め等を除ける。これは量子化部分の約34%減であって、全推論の34%減ではない。まず計算式を変えずに共有する。

`x / scale`を`x * inv_scale`へ変えると除算を減らせるが、丸め境界でint8値が変わる可能性がある。`roundf`を単純なキャストへ変えるのも同値ではない。これらはモデルのlogitsとgreedy結果を確認する別の最適化として扱う。

### RoPEの同じ計算を繰り返さない

現在のhead sizeは16なので、必要な周波数は8種類。それを6層×6ヘッドで繰り返し、ソース上は1forward当たり288回の周波数・三角関数計算になっている。

周波数8個はモデル初期化時に計算し、各位置のsin/cos各8個だけをforwardの冒頭で計算して全層・全ヘッドで共有できる。周波数と当該位置のsin/cosは合計96B。全256位置を保存する場合でもsin/cosは16KiBだが、まず96Bの方式で十分である。同じ数式を使う再利用と、近似関数への置換は分けて評価する。

### 小さな作業配列を内部RAMへ移す

`llm_alloc()`はPSRAM優先なので、KVだけでなく`xq/xs`、活性値、logits、attention作業領域もPSRAMにある。

現在の`x/xb/xb2/q/hb/hb2/att/logits/xq/xs`の合計は14,116B。これらと小さな管理情報を内部RAMへ置き、約590KBのKVはPSRAMに残す分離が扱いやすい。必要ならRMS重み約5KBも加える。ASRの内部RAM優先配列、I2SのDMA領域、各タスクのスタックを確保した後の最大連続空き領域で判断する。

全部のLLM確保を内部RAMへ変更するとKVが収まらない。共有キャッシュで小配列が既に十分に保持されている場合、効果は小さいこともある。内側の積和関数だけをIRAMへ置く試験も候補になる。[Espressifの実行速度最適化](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32/api-guides/performance/speed.html#targeted-optimizations)

### ECO V3なら旧PSRAM回避策の費用を調べる

Core2の申告チップはECO V3だが、現行ビルドは`-mfix-esp32-psram-cache-issue`と最低rev.0向けSDKを使い、逆アセンブルにも`memw`があった。Espressifはrev.3を最低対象にすると旧PSRAM回避策を外せると説明している。[ESP32 rev v3](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32/api-guides/external-ram.html#esp32-rev-v3)

実際のチップrevisionを確認した上で比較する候補である。アプリのフラグだけを外しても、配布済みSDK/Newlibの回避策まで消えるとは限らない。全体への適用はSDK再構築を含むため初手にしない。

## プロンプト一括処理の実現方法と限界

「重みを再利用して読み出し回数を減らす」という方向は正しい。ただし、全プロンプトを1回の単純な行列積で終えられるわけではない。

1. 全トークンの埋め込みを用意する。
2. ある層について、全位置のQ/K/Vをまとめて計算する。
3. 位置ごとのRoPEと、未来のトークンを見ないcausal attentionを行う。
4. 出力射影とFFNを位置方向にまとめる。
5. その結果で次の層へ進む。
6. 最終層の最後のプロンプト位置だけ語彙分類を行う。

N個分の積和は残る。重みのタイルを内部RAMへ読み、4〜8位置分に使い回すなど、**同じ重みを使い切ってから次へ進むループ順**が必要になる。単に現行`llm_forward()`を配列APIで包んでも速くならない。

N=16の状態`X[N][96]`は6,144B、FFN作業配列`H[N][256]`は1枚16,384B。Qや別のFFN配列、量子化、重みタイルも必要なので、追加RAMは数十KB以上を見込む。attentionを全層分保持する必要はなく、層ごと・位置ごとに作業領域を再利用できる。既存KVの層・位置の配置とRoPE位置を維持する。

読み出し待ちが元時間の割合f、重みの再読み出しが理想的にN分の1になるなら、概算速度比は次のとおり。

```text
speedup ≈ 1 / ((1 − f) + f / N)
```

N=16でf=0.3なら約1.39倍、f=0.5なら約1.88倍、f=0.8なら4倍。**6〜16トークンだから全体が6〜16倍速くなる、とはいえない。** フラッシュと小さな配列を先に改善すると残る計算の割合が上がり、一括化の追加効果も小さくなる。

[llama.cppのbatched例](https://github.com/ggml-org/llama.cpp/blob/master/examples/batched/batched.cpp)は、全プロンプトをbatchに入れ、最後の位置だけlogits出力を指定する構成の参考になる。ただしESP32にそのまま載せるライブラリとしての推奨ではない。

## PSRAMへのコピーと2コア化

### 重みのコピーに必要な空き容量

LLM全体は799,912Bなので、申告の空き約0.57MBでは不足する。容量を作る選択肢はある。

- KV長を256から128へすると、K/Vで294,912B、attention作業領域で3,072Bを節約できる。現行の返事上限48トークンを保つ場合、プロンプト上限は207から79トークンに減る。通常の短文には収まるが、長文の仕様は変わる。
- ASR重みをフラッシュに残してLLMをPSRAMへ置く配分を比較する。ASRが多少遅くなっても、毎回答えの前に何度も読むLLM側の利益が上回る可能性がある。両処理の合計で判断する。
- LLMの一部行列だけをPSRAMへ置く方法もある。全コピーの成否だけに限定せず、容量と読取頻度で選ぶ。
- 音声作業領域と3枚のPCMを小分け再生方式へ変えると容量を作れるが、TTSと再生の設計変更になる。バッファを単純に半分にして6秒の句を切り捨てない。

上のKV短縮だけでは、LLMコピー後の余裕は小さい。総空きだけでなく最大連続領域とピーク使用量を測る。PSRAMも外部SPIメモリなので内部RAMと同じ速度ではなく、ASRの14%改善をLLMへそのまま移せない。

ESP32の通常の連続マッピングは4MiBだが、残りを使う[Himem API](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32/api-reference/system/himem.html)は存在し、32KiB単位で切り替える。ローカルSDKではbank switchingも有効だった。ただし既存の重みポインタをそのまま8MB空間へ置くことはできず、ウィンドウ切り替えと同時アクセスの管理が必要になる。まずLLMのホットパスへ入れず、低頻度データの退避候補とする。

### 2コアで分担する場合

各行の内積は独立なので、入力の量子化を1回だけ行い、読み取り専用の`xq/xs`を共有して、出力行を分担する形が自然である。各ワーカーが同じ`matmul()`をそのまま呼ぶと、共通`xq/xs`への書き込みが競合する。

フラッシュ・PSRAM帯域そのものは2倍にならない。短い行列で毎回セマフォを往復すると同期コストも増える。既存ASR用ワーカーの仕組みを参考に、大きいFFNや分類から段階的に比較する。生成開始後はスピーカータスクともCPU・キャッシュを共有するので、速度だけでなく再生の途切れを確認する。

## 音声認識との重ね合わせと応答キャッシュ

### 発話終了の短縮

`END_CHUNKS=35`、1chunk=20msなので700ms。まず25chunk=500ms、その次に18〜20chunk=360〜400msの比較が現実的である。`TAIL_CHUNKS=25`でASRへ500msの末尾を残す現行処理も併せて確認する。終了を400msへ早めれば、元の500ms末尾はまだ収録されていない。

普通の短文、文中の間、ゆっくり話す例、雑音、語尾の弱い発話で、途中切断とASR結果を比較する。終了後に500msの末尾を追加収録してから認識する実装にしてしまうと、短縮の意味が薄れる。

### 現在のASRは完全なストリーミング処理ではない

[asr_core.c](https://github.com/crowpilot/M5stack-zundamon/blob/f7d6a0c3acb81ccc94068ff96f109d3e6bbcf317/firmware/src/asr_core.c#L375)は双方向GRUで、後ろから前へも処理する。途中のCTC結果を最終確定文字とみなしてLLMへ渡すと、後で認識が変わる可能性がある。またASRは既に2コアを使うので、LLMとの同時処理がそのまま利益になるとも限らない。

録音中の特徴量計算、確定できる範囲の畳み込み、無音判定待ちの終盤に仮認識を始める、といった段階的な重ね合わせは候補になる。仮の文字列で先行prefillするなら、最終トークン列と一致する接頭辞だけを再利用し、変更位置以後のKVを作り直す必要がある。先行した返事を誤って喋らせない。初期施策としては固定接頭辞と終了判定の調整の方が簡単である。

### 29フレーズの返事キャッシュ

現行は会話履歴を引き継がない1往復形式で、通常はtemperature=0。そのため、登録フレーズに対する現在のモデルの返事本文と最終タグをPCで先に生成し、フラッシュに保存できる。認識が登録フレーズへ確定したときにだけ使えば、自由入力はLLMへ残せる。ボタンCのtemperature=0.8の別返事は生成経路を使う。

文章・タグ・必要なら読み記法を持ち、現在と同じVCV合成器で喋らせる。モデル・語彙・プロンプト・生成条件でキャッシュを区別し、モデル交換で必ず再生成する。声色まで従来と同じにするなら、最初の句の時点の声色予測も記録する。これは同じgreedy回答の計算場所を移す案であり、別の定型文を手書きする案とは区別できる。

頻出フレーズのKVを保存して毎回生成する案もあるが、現行29フレーズは合計205プロンプトトークンで、独立に全KVを持つと472,320B、さらに最後のlogitsが118,784Bになる。接頭辞共有などで削れるが、既に返事が固定の経路では文章キャッシュの方が軽い。

### 相づちとタグのキャッシュ

認識直後に短い相づちを再生すれば、最初の音は早くなる。例えば0.3秒の16kHz/int16音声は9,600B。ただし改善するのは反応感であり、回答本文が用意できる時刻は変わらない。相づちが長ければ、完成した回答をキューで待たせることもある。困りごとに毎回明るい「うん！」を返す等、内容との不一致にも注意する。

「相づち開始」と「回答開始」を別に記録する。タグだけのキャッシュや、タグ8個の最大値探索の高速化は、主要な待ち時間を減らさない。

## 語彙分類を一部だけ計算する案

出やすいトークンだけ計算して最大値を選ぶ方法では、計算しなかった語が本来の最大値だったか分からない。候補集合にない語、気持ちタグ、終了トークンの確率も失う。greedyの厳密な結果を保つには、未計算部分の上界を証明して枝刈りする等の別の仕組みが必要になる。

まず途中プロンプトの分類を丸ごと省く方が簡単で、本文の品質も保てる。生成時の分類を高速化しても、削れるのは計測した分類時間の範囲内である。線形層MACの13.9%という比率だけで、全推論の同率改善を保証しない。

新語彙では日本語の入力トークン数が減る余地もある。入力が1トークン減れば現状約125ms相当。ただし語彙を大きくすると共有埋め込み・分類層が大きくなり、生成中も毎回重くなる。29フレーズ、自由文、短文、長文についてトークン数と最初の句までの実時間を合わせて評価する。

## 実機での切り分けと着手順

実装担当は次の順で進めると、モデル更新の前後で効果を比較しやすい。

1. **現在の動作条件を記録する。** 初期化後のflash/PSRAM設定、チップrevision、CPU周波数、モデルと語彙のハッシュ、総空きと最大連続RAMを記録する。DIO/40というボード設定を実行時40MHzと同一視しない。
2. **LLMの区間時間を測る。** トークン化、量子化、int8積和、倍率適用、RoPE、attention、FFN非線形、分類層を分ける。プロンプトと生成を分け、TTSと画面描画の時間も別にする。ログは内側ループで出さず、最後に集計して出す。
3. **固定2トークン再利用と途中分類省略を入れる。** PCで同値性を比較し、実機では起動後の初回・別入力を挟んだ再入力・連続会話でも測る。
4. **通知の前倒しと先頭無音の短縮を入れる。** 声色の扱いを明確にし、文字・最終タグ・実音の開始を確認する。LCD描画を音声処理より先に行う必要があるかも確認する。
5. **発話終了判定を段階的に短くする。** 話者の間と語尾を含む録音で、待ち時間と認識品質を比較する。
6. **量子化共有、RoPE再利用、内部RAM化を比較する。** 計測で支配的なものから行う。除算の置換等の数値変更は別々に評価する。
7. **実行時モードを確認してQIOを試す。** 正しいbootloader/SDKを使い、ASR、LLM、TTS、LCDを含む実際の動作で確認する。申告の40MHzと異なるならベースラインを更新する。
8. **残った律速に応じてbatch、2コア、PSRAMコピーへ進む。** 登録フレーズ中心の体験なら、返事キャッシュを独立の最短経路として先に入れてもよい。

フラッシュ律速の確認には、同じ行列サイズで「フラッシュの重みを読むだけ」「内部RAMへ置いた重みで積和」「フラッシュ重みで積和」を比較する。32KB以内の小配列だけで外部帯域を判断せず、LLM相当の約0.8MB走査と、代表行列の両方を測る。読取結果をchecksum等で消費し、最適化で消えないようにする。TTSの`esp_partition_read`とLLMのメモリマップ参照は別経路なので、片方の速度をもう片方に代用しない。

`esp_timer_get_time()`は区間計測に使え、短い関数では特定コアへ固定してcycle counterも使える。Espressifは短い測定のキャッシュ依存と繰り返し測定の必要性を説明している。[性能測定の公式ガイド](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32/api-guides/performance/speed.html#measuring-performance)

最終的な指標は、同じ録音入力に対する「発話終了から回答本文が聞こえるまで」の中央値と遅い側の値にする。相づちを入れる場合は本文とは分ける。電源投入後とウォーム状態、シリアル入力とマイク入力も分けて記録する。

### 初期施策を組み合わせた試算

分類層が17.4ms/回という比例仮定を使うと、固定2トークン、途中分類省略、通知前倒しの合計は次のようになる。

```text
N=6  : 250 + (6−3)×17.4 + 125 ≈ 427ms
N=16 : 250 + (16−3)×17.4 + 125 ≈ 601ms
```

発話終了の短縮200〜350msと先頭無音の短縮70〜80msが成立すれば、合計約0.7〜1.0秒が検証目標になる。フラッシュ変更や大きなモデル変更を含めない試算である。新モデルのトークン数、途中声色の選び方、実音の開始測定によって実際の結果は変わる。

## 参考としてのCoreS3

[CoreS3の公式仕様](https://docs.m5stack.com/en/core/CoreS3)は、240MHzのデュアルコアLX7、16MBフラッシュ、8MB PSRAM。S3のベクトル命令を使うESP-DSP/ESP-NNカーネルは、Core2より適用の余地が大きい。ただしCoreS3の仕様はQuad PSRAMであり、すべてのS3製品がOctal PSRAMという前提にはしない。

S3の19.13 token/sの先行例は、モデルと配置が異なる。現在のモデル・VCVバンク・ASRを同時に動かした速度は移植後の比較が必要である。Core2で上記の局所改善を行ってから、まだ待ち時間やメモリが不足する場合の選択肢とする。

## 引き継ぐ結論

フラッシュの読取速度、一括prefill、固定接頭辞という推測は方向として妥当。ただし、**実行時の40MHzという前提、推論全体10〜30msという計算見積もり、一括化で6〜16倍という期待は修正が必要**である。

Claude側では、まず計測の定義を整え、固定接頭辞・途中分類省略・通知タイミング・先頭無音を小さく分けて実装する。その後、終了判定とホットな演算・メモリ配置を評価する。短縮できた秒数と認識・音声品質を確かめてから、QIO、batch、2コア、重み配置の大きな変更へ進む。

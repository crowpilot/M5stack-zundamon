# 調査・レビュー依頼: M5Stack Core2 上の「ずんだもん」の喋り出しを早くしたい

## お願いしたいこと

M5Stack Core2（ESP32）1台で、音声認識 → 小さな LLM → 音声合成 を全部ローカルで動かしています。
**話し終わってからずんだもんが喋り出すまで（いま約2.5〜3.5秒）を短くしたい**ので、次をお願いします。

1. 下の測定結果から、どこを縮めるのが一番効くかの評価
2. 縮める方法の候補を、効果の大きい順に。それぞれ「見込める短縮幅」「実装の手間」「失うもの（品質・メモリ）」を添えて
3. 私の推測（後述）が正しいかのレビュー。ESP32 のフラッシュ・PSRAM・キャッシュの性能についての実測例や文献があれば出典つきで
4. 似たこと（ESP32 / マイコンでの llama2.c 系 LLM 推論、int8 行列ベクトル積の高速化、プロンプトの一括処理）をしている事例・ライブラリ

条件: **SDカードなし、Wi-Fi・サーバーなし（全部本体で）** は変えたくありません。ハードの買い替え（CoreS3 など）は「参考」として別枠で教えてください。

## ハードウェアとメモリ

| 項目 | 値 |
|---|---|
| 機種 | M5Stack Core2（ESP32-D0WDQ6-V3、Xtensa LX6 デュアルコア 240MHz、SIMD なし） |
| フラッシュ | 16MB（JEDEC ID: メーカー 0x20、デバイス 0x6018）。**今は DIO・40MHz**（PlatformIO の m5stack-core2 ボード定義の既定） |
| PSRAM | 8MB 搭載・使えるのは 4MB（QSPI、40MHz） |
| 内部 RAM | 起動後の空き 約136KB |
| PSRAM 空き | 起動後 約0.57MB（認識モデルのコピー0.7MB、LLM の KV キャッシュ、音声合成の作業領域、再生バッファで使用） |
| フラッシュの使い方 | アプリ 4.5MB（うち使用3.6MB）＋ 音声バンク 9MB（データ領域、`esp_partition_read` で読む） |
| 開発環境 | PlatformIO、espressif32@6.9.0（Arduino-ESP32 2.x / ESP-IDF 4.4）、M5Unified 0.2.26 |

## 処理の流れ

```
マイク(16kHz) → 発話区間検出（700ms 無音で話し終わりと判定）
 → かな音声認識（CNN+GRU、CTC、約0.7MB int8、2コア並列）
 → 登録フレーズ照合（29個）
 → LLM（llama2.c 系、int8）で返事を1トークンずつ生成。画面に逐次表示
 → 句読点（、。！？）まで来たら: 読み辞書でカタカナ化 → VCV 単位接続の音声合成 → スピーカーの待ち行列へ
    （再生は M5Unified のスピーカータスクが裏で行い、その間に LLM は次の句を生成）
```

### LLM（いちばん時間がかかる部分）

| 項目 | 値 |
|---|---|
| 構造 | llama2.c 互換。dim 96、hidden 256、6層、6ヘッド（KV 3ヘッド）、語彙 1024、seq_len 256。分類層は埋め込みと共有 |
| パラメータ | 約70.8万。int8（グループサイズ32、fp32 の倍率つき）、ファイル 0.80MB |
| 置き場所 | **フラッシュに埋め込んだ const 配列をそのまま読む**（PSRAM にはコピーしていない） |
| KV キャッシュ | fp32、PSRAM |
| 行列ベクトル積 | 素直な C（入力を int8 に量子化 → 行ごとに int8×int8 を int32 で積算 → 倍率を掛ける）。1コアのみ |
| 入力の形 | `<BOS>Ａ：{話しかけ}Ｂ：` を1トークンずつ forward（プロンプトもトークンごとに逐次） |
| 生成 | greedy。返事は5〜12トークン、最後に気持ちタグ |

## 測定結果（実機、シリアル入力で認識を飛ばして測定、v0.0.2）

「処理開始」は話しかけの文が LLM に渡った時点。

| 話しかけ | プロンプトのトークン数 | 1トークン目が出るまで | 喋り出し | 返事のトークン数 | 生成の合計 |
|---|---|---|---|---|---|
| おはよう | 6 | 0.87秒 | 1.43秒 | 5 | 1.43秒 |
| こんにちは。 | 9 | 1.26秒 | 1.93秒 | 11 | 2.66秒 |
| 今日はいい天気ですね | 12 | 1.63秒 | 1.79秒 | 10 | 2.90秒 |
| 上司が厳しくて困ってる | 15 | 2.02秒 | 2.17秒 | 7 | 2.91秒 |
| テストで100点とったよ！ | 16 | 2.14秒 | 2.30秒 | 8 | 3.17秒 |

- **forward 1回あたり約125ms**（プロンプト中も生成中もほぼ同じ。生成中は音声合成と再生が重なって約140ms）
- 喋り出しまでの大半はプロンプトの処理（6〜16トークン × 125ms）
- 音声合成は1句あたり35〜90ms（2〜3秒の音声）。認識は約0.3〜0.6秒
- 実際に人が待つ時間は、上の「喋り出し」に **話し終わり判定の700ms ＋ 認識0.3〜0.6秒** が足される → 約2.5〜3.5秒

## 私の推測（レビューしてほしい点）

1. **LLM はフラッシュの読み出し速度で律速している**のでは。1トークンごとに重み0.8MB を全部読む。DIO・40MHz のフラッシュをキャッシュ経由で読むと、実効で毎秒数MB程度？ そうなら 0.8MB ÷ 6MB/s ≈ 130ms で、測定の125ms と合う。計算量は約70万回の int8 積和なので、240MHz なら本来 10〜30ms で済みそう
2. そうだとすると、効きそうな順に:
   - (a) **フラッシュを QIO・80MHz にする**（Core2 のフラッシュが対応しているか？ ブートローダの設定、PSRAM と同じ SPI バスとの兼ね合いは？）
   - (b) **プロンプトの一括処理**: 全プロンプトトークンを1回の行列×行列でまとめて計算すれば、重みを読むのは1回で済む（KV キャッシュは位置ごとに作る）。6〜16倍の読み出しが1回になる
   - (c) LLM の重みを PSRAM にコピー（認識モデルでは+14%だった。ただし PSRAM の空きが足りない）
   - (d) 2コアで行を半分ずつ（読み出し律速なら効かない？）
3. 固定部分の前計算: `<BOS>Ａ：` の KV を起動時に作っておけば、毎回2トークン（約250ms）省ける
4. 話し終わり判定の700ms を縮める・認識と LLM のプロンプト処理を重ねる、など処理以外の工夫

## ほかに考えている案（評価してほしい）

- 返事の最初に短い相づち（「うん！」「えっとね」など）を事前合成しておき、認識直後にすぐ流す
- 気持ちタグ・返事の頻出パターンのキャッシュ
- 語彙 1024 の分類層（1024×96）を、出やすいトークンだけ先に計算する
- モデルをさらに小さくする／層を減らす（品質とのトレードオフ）
- ESP-IDF の esp-nn・ESP-DSP などのライブラリが ESP32（S3 でない）で int8 行列ベクトル積に効くか

## 変えられない・変えたくない条件

- SDカードなし（フラッシュ 16MB に全部入れる）、ネットワークなし
- 音声合成は VOICEVOX:ずんだもん の単位音声を使う方式のまま
- LLM の出力形式（漢字かな交じり＋最後に気持ちタグ）は変わらない。モデルは近く新しい版（語彙を作り直し）に差し替える予定
